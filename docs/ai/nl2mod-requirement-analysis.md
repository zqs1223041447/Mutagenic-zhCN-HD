# 自然语言需求分析规则

> **角色**：L2 子文档。处理"用户用自然语言提出 MOD 功能需求"时的需求分析规范。
> **使用方式**：**按需加载，不进入 Preflight 固定读取**。当任务匹配 `.opencode/skills/nl2mod-requirement-analysis/` 触发条件时，由 skill 引导加载本文件。
> **权威**：本文件与 AGENTS.md / status.json 冲突时，以 AGENTS.md / status.json 为准。

---

## 1. 基本原则

用户输入的自然语言，默认先作为**需求描述**处理，不直接视为执行命令。

AI 必须按以下顺序处理：

```text
读取需求
→ 理解含义
→ 区分事实 / 猜测 / 问题 / 功能需求 / 待办
→ 检查游戏当前实现
→ 分析可行性
→ 给出方案
→ 等待用户确认
→ 执行
→ 构建与验证
```

未经明确确认，不修改工作区。

---

## 2. 自然语言分类

AI 应识别以下类型：

- `QUESTION`：询问当前是否存在某功能
- `OBSERVATION`：用户观察到的现象
- `HYPOTHESIS`：尚未确认的猜测
- `BUG`：已有功能可能存在问题
- `FEATURE`：希望增加的新功能
- `LOCALIZATION`：汉化问题
- `REFERENCE`：参考外部游戏或 POEDB
- `TODO`：明确暂不实现
- `PLACEHOLDER`：X、某地图、若干等未确定参数

例如：

> 投射物似乎是无限射程，暂时没确认。

必须先标记为 `HYPOTHESIS`，调查确认后才能讨论修改。

---

## 3. 不得擅自补全需求

对于：

```text
X 套天赋树
特定地图待办
某些道具
若干属性
```

AI 不得自行决定具体值。

可以分析实现方式，但必须把这些内容标记为"未确定"。

---

## 4. 问题与功能需求必须分开

例如：

> 是否具有实时保存功能？

这里只要求调查当前保存机制。

不能自动解释成：

> 增加实时保存功能。

例如：

> 装备菜单没有快捷键。

应先调查：

- 是否已有 InputMap；
- 是否存在未绑定快捷键；
- 是否只能通过 UI 打开；
- 是否确实缺少该功能。

确认不存在后，才能提出增加快捷键方案。

---

## 5. 用户提出的实现方式只是候选方案

例如：

> 按照存活时间 × 投射物速度判断射程。

AI 应理解为设计建议，而不是强制实现。

需要先检查游戏投射物机制，再比较：

```text
存活时间 × 速度
```

与：

```text
实际累计飞行距离
```

等方案，选择更符合现有架构的方法。

---

## 6. 汉化问题优先寻找根因

例如：

> "16%提高 伤害 with 法术 skills"

应先检查：

- 动态文本模板；
- 属性词条组合；
- 术语映射；
- 未覆盖字符串。

优先修复产生同类英文混杂的公共机制，不只修示例字符串。

---

## 7. POEDB 规则

项目中的 **POEDB** 特指：

```text
poedb.tw
```

POEDB 是本项目未来的重要长期参考信息库。

主要用于研究：

- 投射物机制；
- 异常状态；
- 装备词缀；
- 传奇物品；
- 特殊装备机制；
- crafting；
- 地图机制；
- 掉落机制；
- 其他可借鉴的 ARPG 系统。

涉及 POEDB 的需求，应按照：

```text
读取 POEDB 信息
→ 理解 POE 机制
→ 检查 Mutagenic 当前机制
→ 对比差异
→ 判断哪些适合移植
→ 设计 Mutagenic 本地实现
```

不能直接假定 POE 与 Mutagenic 实现一致。

POEDB 用于**机制和数据参考**，不是要求复制 POE 的代码结构。

---

## 8. 特殊机制优先做成本地通用能力

例如：

> 某传奇物品：召唤物死亡时玩家掉血。

优先考虑：

```text
召唤物死亡事件
→ 装备效果检测
→ 玩家生命效果
```

而不是把特殊代码散布到每一种召唤物脚本中。

大量 POEDB 传奇物品未来应尽量建立：

```text
Trigger
Condition
Effect
```

这类通用机制，再由物品数据引用。

---

## 9. 执行权限

默认状态：

```text
只读分析
```

用户明确表示：

```text
执行
开始修改
按这个方案做
实现它
```

之后，才允许修改 MOD / 脚本 / 汉化等工作文件。

构建 Candidate 后仍然：

```text
不得自动晋升 baseline
```

原有不可变目录、禁止 F 盘、密钥不入库、fresh embed 等规则始终有效。

---

## 10. AI 每次分析的输出格式

保持简洁，只需要：

### 需求理解
AI 如何理解用户描述。

### 当前情况
已确认 / 未确认 / 需要调查。

### 可行性
使用：

```text
可行
需要底层改造
需要进一步调查
不建议
阻塞
```

### 推荐方案
说明建议修改哪个系统。

### 未确定项
例如 X、地图、具体数值。

### 执行范围
如果用户确认执行，将修改哪些内容。

在没有得到执行授权时停止在这里。

---

## 11. 当前需求示例解释

```text
实时保存
→ 调查问题，不是新增功能要求

装备菜单快捷键
→ 先确认是否已有输入机制

X 套天赋树
→ 新功能，X 未确定

道具仓库
→ 新功能，先调查 inventory/save/UI

投射物无限射程
→ 未确认假设，先验证

天赋树中英混杂
→ 汉化 BUG，优先检查动态模板

POEDB 投射物
→ 机制对比研究

POEDB 异常状态
→ 对比两套状态系统

POEDB 传奇物品
→ 长期功能方向，优先建立通用特殊效果系统

POEDB crafting
→ 先读取和整理机制，再设计简化版
→ 具体地图绑定属于待办
```

## 12. 核心约束

> 不把猜测当事实。  
> 不把问题自动变成功能需求。  
> 不擅自填写未知参数。  
> 不把用户建议的方法当成唯一实现。  
> 先调查现有机制，再设计 MOD。  
> POEDB 作为长期重要参考源。  
> 未经用户确认，只分析，不执行。
